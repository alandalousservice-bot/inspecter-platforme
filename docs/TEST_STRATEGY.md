# Test Strategy v0.1

تحدد [IMPLEMENTATION_PLAN](IMPLEMENTATION_PLAN.md) الحد الأدنى لكل مهمة؛ لا تختبر تفاصيل داخلية بلا قيمة. Unit بـVitest لقواعد النطاق، API integration على PostgreSQL اختبار معزول، Playwright لمسارات حرجة بمتصفح حقيقي. اختبارات SQL/migrations على قاعدة اختبار لا production. Fixtures اصطناعية فقط، لا بيانات شخصية حقيقية.

TASK-030: اختبر POST عربيًا صحيحًا وإيصال `202` بالحقول المحددة فقط و`no-store`، وكل حد طول عند القيمة القصوى وفوقها (Unicode code points)، والقيم الأربع للوضعية ورفض غيرها، وقاعدة الهاتف الثابت/المحمول المحلي و`+213`، والتواريخ الصحيحة والحدود الزمنية، والفراغات ومحارف التحكم و`null` والمفاتيح المجهولة وJSON المعطوب. اختبر المؤسسات 0..5 إضافية ورفض التكرار الأساسي/الإضافي بعد التطبيع؛ UUID غير صالح/مقاطعة غير موجودة/بلا عضوية حالية دون كشف سبب `404`. تحقق أن المحاولات الصحيحة وvalidation المرفوضة تدخل حد 10/IP/15 دقيقة وأن `429` يعيد `Retry-After`، وغياب IP موثوق يفشل مغلقًا. اختبر أن كل POST صالح ينتج TeacherSubmission مستقلًا `PENDING` حتى مع إعادة الإرسال والتزامن ودون `Idempotency-Key`، ولا ينشئ Teacher أو Institution أو Assignment أو AuditLog، ولا public lookup أو PII في الرد/الأخطاء/السجلات، مع migration clean+upgrade على قاعدة معزولة.

TASK-032: اختبر أن تطابق الهاتف المعياري، والبريد وفق تطبيع النطاق دون تغيير الجزء المحلي أو aliases، والاسم الأول واللقب بعد NFC/اختزال الفراغات مع تاريخ الميلاد ينتج كلٌّ منها المرشح وسبب `SAME_PHONE/SAME_EMAIL/SAME_NAME_AND_DOB` المناسب، وأن المرشح الواحد قد يحمل أسبابًا متعددة. اختبر عدم الاكتفاء بالاسم نفسه مع DOB مختلف، أو DOB وحده، أو مكان الميلاد أو المؤسسة وحدهما؛ وعدم طيّ اختلافات الحروف العربية/التشكيل/الترقيم أو استخدام fuzzy matching، مع بقاء شخصين متشابهين مختلفين. اختبر إدراج `PENDING/INTERNAL_REVIEW` واستبعاد `REJECTED` والطلب الحالي، وعزل District وعدم اطلاع مفتش غير مصرح أو غير مصادق على الطلب أو مرشحيه. اختبر أن القائمة تعرض مؤشرًا منطقيًا فقط وأن التفصيل يعيد ملخص المرشح وأسبابه دون PII غير اللازمة، ولا يوجد public duplicate disclosure أو mutation أو persistence للمرشحين أو PII في logs/errors؛ افحص المسارات على PostgreSQL اختبار معزول مع حالات تطبيع عربية وUnicode.

TASK-033 UI/component tests: اختبر إجراءات `PENDING` و`INTERNAL_REVIEW` وفق مصفوفة ADR-026، وعدم وجود إجراءات للحالات النهائية؛ حوارات التأكيد والرجوع والإلغاء والتركيز ولوحة المفاتيح ومنع الإرسال المكرر؛ تحذير التشابه المحايد لا يعطل قرارًا صحيحًا ولا يدمج ولا يعرض confidence؛ لا حقل سبب رفض أو ملاحظة مراجعة؛ عرض آمن لـ409 والخطأ العام؛ RTL/responsive/accessibility؛ ومسار الإنتاج يبقى read-only ولا يعرض إجراءات فعالة قبل TASK-034. لا تختبر إنشاء Teacher أو DB mutation في TASK-033.

TASK-034 integration tests: فرض مصفوفة ADR-026 على الخادم؛ جسم strict و`expectedStatus` الإلزامي وسباقات `409` بلا إعادة. قبول ينشئ Teacher واحدًا ويضبط `acceptedTeacherId` كرابط FK فريد؛ تحقق من mapping كل حقول ADR-027، و`recordStatus=ACTIVE` و`archivedAt=NULL`، وأن `confirmationDate/qualifications` المحذوفتين تصبحان NULL؛ تحقق من بقاء الحقول المطلوبة في intake مُلزمة رغم nullable Teacher. `notes` وأسماء المؤسسات وreceipt/decision metadata لا تُنسخ، ولا PII uniqueness أو Teacher.notes؛ رفض/مراجعة لا ينشئان Teacher، ومراجعة داخلية فقط من PENDING، ولا Institution أو Assignment. اختبر `decidedAt/decidedByInspectorId` لكل إجراء، AuditLog واحدًا بmetadata المسموح لكل قرار وفشل append يُرجع المعاملة كلها. أرسل ACCEPT مكررًا بعد النجاح، وطلبين متزامنين: فائز واحد كحد أقصى، والخاسر `409` بلا Teacher/AuditLog إضافي ولا replay؛ لا `Idempotency-Key` مطلوب، وعميل TASK-033 لا يرسله بعد التكامل. مرشحو التشابه لا يمنعون القرار ولا يُعرض المصدر المقبول وTeacher الناتج مرتين؛ لا Teacher-comparison engine ضمن هذه المهمة. اختبر auth/CSRF/district scope، واستجابة النجاح المحدودة، وclean/upgrade migration على قاعدة اختبار معزولة. اختبر تفعيل عناصر TASK-033 فقط مع endpoint عامل.

TASK-035 API/DB tests: GET/PATCH يشترطان Inspector `ACTIVE` وعضوية حالية؛ اختبر جلسة غائبة/معطلة، عضوية منتهية/مستقبلية، و404 عام للمعرّف الغائب أو خارج النطاق وUUID مشوه. GET يعيد الحقول المحددة وتواريخ `YYYY-MM-DD` وسياق المؤسسات المعلنة من الطلب المقبول فقط، دون snapshot كامل أو notes/receipt/decision metadata أو AuditLog قراءة. تفصيل submission لا يكشف `acceptedTeacherId` خارج النطاق، ويظهر رابطًا فقط بعد قبول مرتبط. PATCH يختبر كل حقل على حدة، الجزئي والإبقاء على المحذوف، مسح nullable بـ`null`، رفض null لـ`name/surname`، رفض `""`، الجسم الفارغ/المفاتيح غير المعروفة/حقول النطاق والحالة والأرشفة والمصدر، والحدود Unicode ومحارف التحكم والتواريخ الحقيقية/المستقبلية والكرونولوجيا بعد الدمج والهاتف الجزائري والبريد والوضعيات الأربع. لا merge أو منع تحديث بسبب PII مكرر. اختبر تغير `updatedAt` عند التعديل فقط، وno-op دون AuditLog، وحدث `TEACHER_PROFILE_UPDATED` واحدًا بأسماء الحقول المتغيرة فقط دون قيم PII، وأن فشل append يرجع PATCH. يبقى submittedProfile وقرار الطلب وInstitution/Assignment وعدد Teachers دون تغيير؛ لا migration لـTASK-035. اختبر آخر كتابة ناجحة للحقل نفسه دون version precondition والحقول غير المذكورة دون فقد.

TASK-035 UI/G3: عرض/تحرير/إلغاء/حفظ مع loading/error/success وvalidation محلية/خادمية، منع double-submit، عدم التحديث المتفائل، focus/keyboard وRTL/responsive. حالات `ACTIVE/INACTIVE` بتسميات عربية read-only، والتصريحات الأصلية موسومة غير معتمدة ولا حقول تعديل لها، ولا حساب أستاذ أو قائمة/إسناد/زيارة. اختبر مسارًا متكاملًا public POST → قائمة/تفصيل المفتش وتنبيه التشابه → تأكيد ACCEPT → `acceptedTeacherId` من تفصيل مصرح → GET وواجهة Teacher → PATCH مسموح → snapshot الأصلي ثابت؛ ومساري REJECT وINTERNAL_REVIEW والسباق/الخصوصية. تظل اختبارات TASK-020..034 خضراء قبل غلق G3.

عند كل task: tests الخاصة به، typecheck، lint، build عند تغير wiring، regression مرتبط بالموديول. Gate المرحلي يتطلب الأدلة لا مجرد نجاح الأمر. لا يجري اختبارات إنتاج أو migrations عليه في هذه المرحلة.

## Connected browser gate

- Playwright + Chromium هو مسار E2E المتصل المعتمد؛ الاختبار الأساسي `e2e/g3-connected-flow.spec.ts` ويستخدم `npm run e2e:g3` لإعداد API وVite وتشغيلهما دون خدمات بعيدة.
- الأمر يقرأ credential من `D:\pg-task020-temp\task020-test-url.secret`، ويتحقق قبل الاتصال أن الهدف `127.0.0.1:55432/task020_test` بدور `task020_test_user`. لا يطبع أو يحفظ connection string في ملفات المشروع. يطبق migration chain في schema مؤقتة باسم فريد ويزيل ذلك schema عند انتهاء الاختبار.
- Fixtures اصطناعية فقط؛ واجهة المتصفح تنفذ public submission وقرارات Inspector وTeacher PATCH عبر API الفعلي وCSRF الحقيقي. Prisma في الاختبار يستخدم للتهيئة/التحقق من invariants فقط.
- اختبارات قاعدة البيانات TASK-020..035 عبر `npm run test:db` تتطلب `TEST_DATABASE_URL` مؤقتًا إلى قاعدة الاختبار المعزولة ذاتها؛ يمنع استخدام port 5432 أو أي قاعدة بعيدة/إنتاجية. مخرجات Playwright (`test-results/` و`playwright-report/`) مؤقتة ولا تُتبع في Git.
