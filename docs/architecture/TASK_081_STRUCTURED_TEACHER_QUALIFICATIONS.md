## Model and migration

Add exactly one `TeacherQualification` child model/table; Teacher has zero or more children. Final fields:

| Field | Prisma / PostgreSQL type | Required | Validation and semantics |
|---|---|---|---|
| `id` | `String @id @default(uuid()) @db.Uuid` / UUID | yes | Stable server-generated row identity; not a certificate/business identifier. |
| `teacherId` | `String @db.Uuid` / UUID | yes | Parent Teacher; server takes it only from the scoped path, never a mutation body. |
| `name` | `String @db.VarChar(200)` / varchar(200) | yes | «الشهادة»: certificate/qualification label, 1–200 Unicode codepoints after normalization. |
| `issuingBody` | `String? @db.VarChar(200)` / nullable varchar(200) | no | «مصدرها»: issuer/source as free text, 1–200 codepoints when present; NULL means not supplied, not verified. |
| `qualificationDate` | `DateTime? @db.Date` / nullable DATE | no | «تاريخها»: calendar date only, ISO `YYYY-MM-DD` on the API; no issue/graduation/award-date claim, time zone, inferred chronology, or fabricated value. |
| `createdAt` | `DateTime @default(now())` / timestamp | yes | Creation timestamp generated by persistence. |
| `updatedAt` | `DateTime @updatedAt` / timestamp | yes | Last effective mutation; no-op PATCH does not change it. |

For `name` and supplied `issuingBody`: NFC, trim outer Unicode whitespace, collapse internal Unicode whitespace to one space, reject control characters, count Unicode codepoints after normalization. Do not truncate. `name` cannot be blank/null; omitted optional fields become NULL. Supplied `issuingBody: null` clears it, but `""` or whitespace-only is invalid; a caller should omit an unknown optional value. `qualificationDate` accepts only a real calendar date with exact `YYYY-MM-DD` form, or NULL; no time/timestamp and no guessed future-date restriction. Zod is the API boundary, including strict object keys. Database NOT NULL, varchar limits, and CHECK for nonblank trimmed text guard persistence; API owns NFC/control validation. Use the established safe validation error envelope; never echo rejected values.

Teacher FK: `teacherId → Teacher.id`, `ON DELETE RESTRICT`, `ON UPDATE CASCADE`, consistent with the existing Teacher child pattern. No Teacher deletion or cascade through these routes. No business unique constraint on `name`, `issuingBody`, date, or their combination: same-named certificates may have different row IDs. Only primary-key uniqueness applies. A single teacher-leading retrieval index shall support the order below; no separate redundant `teacherId` index. SQL index expression/order may be written in the one migration when Prisma cannot express NULL placement.

Deterministic order for scoped collection and future card: `qualificationDate DESC NULLS LAST, createdAt DESC, id DESC`. Dated rows sort by the declared date; unknown-date rows sort only by creation time and ID, with **no inferred qualification date**. Do not add a manual position field.

Exactly one additive, forward-only TASK-081 migration from the TASK-080 baseline. Add only the child table, FK, checks and retrieval index plus the Prisma Teacher relation. No edits to previous migrations. No backfill, parsing, update or cleanup of `Teacher.qualifications`; existing Teachers receive zero child rows. Demonstrate clean-chain apply and upgrade from the committed TASK-080 baseline with existing legacy text. DB validation later is permitted only after verifying the isolated target is `127.0.0.1:55432/task020_test` as `task020_test_user`; never 5432, remote or Production; never print the connection string.

## Existing legacy contract

`Teacher.qualifications` is a distinct editable free-text Teacher-profile field under its existing API; preserve its bytes and behavior. It is not a serialized view of the child rows. Do not rename, remove, parse, overwrite, clear, copy, backfill or auto-deduplicate it. The existing public TeacherSubmission qualifications declaration and acceptance flow remain unchanged. Structured rows are Inspector-entered only; no public declaration, receipt, acceptance conversion or duplicate-matching change in TASK-081. No auto-merge between legacy and structured data.

## Inspector API and scope

All paths are authenticated Inspector API under `/api/v1`. Require an ACTIVE Inspector session, the existing CSRF guard for mutations, `Cache-Control: no-store`, request ID/error envelope, and **current** membership in the Teacher's district using the established scope helper. Lookup the Teacher and authorize it before returning children; every child ID must belong to that path Teacher. Missing, wrong-parent, out-of-district and repeated-deleted resources get the same generic 404 behavior, without cross-district existence disclosure. Invalid UUID/body returns the established safe 400 validation envelope. Never trust a body `teacherId` or district ID. No independent global qualification endpoint.

| Method / path | Request | Success | Behavior |
|---|---|---|---|
| `GET /teachers/:teacherId/qualifications` | no query/body | 200 `{ "items": [Qualification] }` | Teacher-scoped, deterministic order above; empty is `{ "items": [] }`. No pagination for this child collection in TASK-081. |
| `POST /teachers/:teacherId/qualifications` | strict `{ name, issuingBody?, qualificationDate? }` | 201 `{ "data": Qualification }` | Create one Inspector-managed row; absent optional values persist NULL. |
| `PATCH /teachers/:teacherId/qualifications/:qualificationId` | strict nonempty subset `{ name?, issuingBody?, qualificationDate? }` | 200 `{ "data": Qualification }` | `name` if sent must be valid non-null; optional fields accept NULL to clear; omitted keys stay unchanged. |
| `DELETE /teachers/:teacherId/qualifications/:qualificationId` | no body | 204, empty body | Physically remove only that child, atomically with its audit event. Missing/repeated/wrong-parent returns generic 404. |

`Qualification` response contains exactly `id`, `name`, `issuingBody` (nullable), `qualificationDate` (nullable ISO date), `createdAt`, `updatedAt`. Parent ID is conveyed by the path, not duplicated in the response. No free-text legacy field in this nested response. No search, bulk create, separate read-by-ID, public write or other CRUD endpoint is implied. The restricted physical DELETE is a correction/removal policy **only for Inspector-managed current qualification child rows**. It does not decide ADR-014's general retention/deletion rules or authorize deletion of Teacher, reports, historical snapshots or AuditLog.

## Concurrency, no-op and audit

Follow Teacher profile's transactional mutation pattern: in each POST/PATCH/DELETE transaction lock the parent Teacher row `FOR UPDATE`, re-read it and check current district membership inside that transaction; for PATCH/DELETE check the child's `teacherId` after the parent lock. This serializes qualification mutations for one Teacher with existing Teacher-profile writes without introducing a global revision contract. A PATCH compares normalized persisted values; if semantically identical, return current row with no database update, `updatedAt` bump or AuditLog row. Concurrent actual PATCHes serialize; later write to the same field wins after re-read, while omitted fields preserve the latest committed values. This is the existing profile-style merge policy, not a new optimistic revision protocol. An unauthorized request never writes or audits.

Add three strict audit actions to the existing allowlist: `TEACHER_QUALIFICATION_CREATED`, `TEACHER_QUALIFICATION_UPDATED`, `TEACHER_QUALIFICATION_DELETED`. For all: `entityType=TeacherQualification`, `entityId=child UUID`, `actorInspectorId` from session, `districtId` from scoped Teacher, `requestId` from request, and append in the **same transaction** as the mutation. Metadata is structural only: `{teacherId}` for create/delete; `{teacherId, changedFields}` for effective PATCH, with sorted unique names drawn only from `name`, `issuingBody`, `qualificationDate`. No qualification values, legacy text, free prose, credentials, dates, names or issuing bodies in metadata, errors or application logs. AuditLog schema stays unchanged. Deleting a child never deletes its immutable AuditLog event; its UUID remains an audit reference, not a FK to a live child.
