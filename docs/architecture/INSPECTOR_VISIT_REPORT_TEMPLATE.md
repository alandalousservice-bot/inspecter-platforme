# نموذج تقرير زيارة المفتش المعتمد للمنصة — جرد وعقد معماري

الحالة: [ADR-034](../DECISIONS.md#adr-034--product-owner-adopted-inspector-visit-report-template) `ACCEPTED`؛ هذا عقد معماري/جرد، لا ينفذ migration أو API أو UI. المصدر صفحتا `IMG_20260930_0001.pdf` و`IMG_20260930_0002.pdf` المقدمتان من Product Owner خارج المستودع. النموذج **معتمد للمنصة** فقط؛ لم يُتحقق من نسبته إلى الوزارة أو إلزامه الوطني. النسختان ممسوحتان ومعبأتان؛ القيم والأسماء والنصوص والتوقيع والختم فيها أمثلة بيانات، لا تعليمات أو enum. لا تُنسخ بيانات الأشخاص من المصدر إلى fixtures أو المستودع.

مفتاح التصنيف: A متاح في النموذج الحالي، B يحتاج لقطة عرض تاريخية، C إدخال مفتش منظم، D نثر يكتبه المفتش، E للطباعة المادية فقط، F غير واضح/غير محسوم. قد يجتمع A وB: قيمة حية موجودة، لكن استعمالها في FINAL يتطلب تجميدها. وجود خانة لا يجعلها إلزامية رقميًا.

القيم النوعية الظاهرة في المثال تشمل «نعم»، «موجود»، «مقبول»، «حسن»، «جيدة»، «فعالة». هي **إجابات تعبئة** وليست قائمة مغلقة ولا درجات. لكل معيار مفتاح ثابت ضمن قاموس القالب Version 1، وقيمته نص قصير اختياري من المفتش مع Unicode/NFC والتحقق المتسق مع API المشروع؛ لا boolean إلزامي ولا enum عام أو scoring. الإرشادات متعددة الأسطر اختيارية والخلاصة مطلوبة عند FINAL. الأسماء التقنية للمفاتيح وحدود النص الدقيقة تُوثق في عقد مهمة التنفيذ، دون اختراع مفردات منتج جديدة.

## مقارنة الحقول السبعة الحالية

| حقل ADR-012 | النوع الجديد المعتمد | حفظ القديم |
|---|---|---|
| `levelClass` | MAP إلى «القسم»، مع إبقاء القيمة القديمة كما هي | لا حذف/إعادة تفسير |
| `lessonTopic` | MAP إلى ميدان/موضوع الدرس؛ «هدف الدرس» ADD مستقل | لا حذف |
| `pedagogicalObservations` | SPLIT إلى معايير ملاحظة منظمة؛ لا تحويل نص قديم آليًا | يبقى للنصوص القديمة |
| `strengths` | DEPRECATE_FOR_NEW_TEMPLATE إن لم يُظهر مصدر الورقة قسمًا مكافئًا؛ لا إخفاء في النوع القديم | يبقى |
| `improvementAreas` | DEPRECATE_FOR_NEW_TEMPLATE كحقل مستقل؛ يمكن التعبير عنه في معايير/إرشادات لكن لا نسخ ضمني | يبقى |
| `guidanceRecommendations` | MAP معنوي إلى «الإرشادات التربوية»؛ SPLIT إلى عنوانين فرعيين للنوع الجديد إذا تأكدت البنية | يبقى نصًا قديمًا |
| `inspectorConclusion` | KEEP/MAP إلى «الخلاصة» | يبقى |

`Visit.academicYear/occurredAt/institutionNameSnapshot` DERIVE تاريخيًا. Inspector/Teacher name snapshots الحالية KEEP؛ الميلاد/المؤهل/البلدية/المقاطعة/القيم المهنية المعروضة تحتاج SNAPSHOT مخصصًا للنوع الجديد عند FINAL إن اعتمدت، وإلا قد تتغير الطباعة لاحقًا. لا تمديد Teacher master لمجرد خانة ورقية؛ القيم غير المتاحة/الناقصة ينبغي تأكيد مصدرها أو إدخالها في التقرير وفق قرار Product Owner. لا استعمال Teacher.institutionId الحالية لسياق زيارة سابقة.

## بدائل البنية وحدود الترحيل

العقد المعتمد: `InspectionReport` بنوع مستقل `INSPECTOR_VISIT`، ومصدر `PRODUCT_OWNER_ADOPTED`، و`templateVersion=1`؛ يثبت الخادم الثلاثية عند إنشاء التقرير ولا يغيرها لاحقًا. يبقى زوج ADR-012 القديم ثابتًا، ويظل `visitId @unique`، لذا يتعايش النوعان عبر زيارات مختلفة لا تقريرين للزيارة نفسها. تقرير قديم DRAFT يظل على محرره القديم؛ لا تبديل تلقائي إلى الجديد. migration مستقبلية forward-only توسّع قائمة الأنواع وتضيف قيودًا شرطية، دون تعديل صفوف قديمة. شرط FINAL القديم يبقى خاصًا بالنوع القديم؛ الجديد يتطلب سياق الحصة الأساسي (`levelClass`, `lessonTopic`) والخلاصة وهوية/سياق الزيارة كما في دورة ADR-012؛ بقية خانات الورقة اختيارية، ولا تمنع القيم المفقودة الإتمام.

بديل جدول تقرير ثانٍ يفصل المحتوى لكنه يكرر lifecycle/authorization ويكسر مرجع `FollowUp.reportId` أو يتطلب علاقة متعددة الأشكال؛ أعلى مخاطرة G5. أعمدة صريحة لكل معيار تسمح بقيود SQL مباشرة، لكنها كثيرة وهشة عند تعديل القالب؛ JSON مؤطر بإصدار يسهل تغييره لكنه يصعّب الاستعلام والقيود والفهارس وقد يتحول إلى مخزن حر. يُعتمد سجل ملاحظات تابع منظم (`reportId`,`criterionKey`,`valueText`، مع قاموس مفاتيح وترتيب وتسميات ثابتة لكل templateVersion)، وقسمان نثريان للإرشاد، ولقطة عرض للحقول الخارجية اللازمة. تفاصيل المفاتيح والحدود الفيزيائية تُثبت في عقد التنفيذ؛ لا migration الآن. لا `recommendationReference` في FollowUp.

الـFINAL يبقى ثابتًا؛ لا تعديل المعايير أو اللقطات أو النصوص بعده، ولو تغيّر Teacher/Institution/District. القيم الموجودة تُستمد من النظام الموثوق؛ المفيدة غير الموجودة تُدخل اختياريًا في التقرير وحده، ولا تُكتب في Teacher/Visit. لا نكرر Visit التاريخي عندما يكفي، لكن اسم المقاطعة والبلدية ليسا لقطة في Visit؛ تجميدهما عند الإتمام يحفظ **ما ظهر وقت الإتمام** فقط، لا يدّعي إعادة بناء وضعهما يوم الزيارة إن تغيّرا قبله. لا اختلاق لقيمة ناقصة ولا منع FINAL لمجرد غياب خانة ورقية اختيارية. التصحيح/النسخ/إعادة فتح نهائي خارج العقد.

الـAPI المستقبلية: GET يميز النوع/الإصدار ويرد إسقاطًا خاصًا بالقالب؛ PUT المسودة يحفظ الحقول/المعايير كاملة بتحقق strict و`expectedRevision`؛ POST finalization يستخدم atomic snapshots + `INSPECTION_REPORT_FINALIZED` مع `metadata={}` بلا PII/نثر، وبنفس scope/CSRF/no-store/error envelope. لا تغيير لمسارات أو إسقاط ADR-012 الحالي قبل عقد التنفيذ التفصيلي. العلامة اليدوية تُحفظ كنص اختياري كما كُتبت؛ لا حاجة تقنيًا إلى مجال رقمي ما دامت لا تُحسب ولا تُرتب. حروف العلامة، إن أدخلها المفتش، نص اختياري مستقل بلا تحويل أو فرض توافق حسابي. واجهة RTL مقسمة بنفس ترتيب المصدر، تنقل بين أقسام، قيم Visit/Teacher مشتقة للقراءة مع تأكيد الناقص، حفظ صريح ومسودة/إتمام وتحذير immutable، ومعاينة طباعة مستقبلية. الطباعة A4 عربية بترتيب وبنية رأس صفحتي المصدر ونصوصه الإدارية الثابتة في Template V1، وقيم موثوقة تُملأ تلقائيًا، ومواضع توقيع/ختم مادية فقط، مع pagination واعية بامتداد النص؛ لا ضمان صفحتين حرفيًا لكل طول نص، ولا طباعة الآن أو دمجها في TASK-060. لا ادعاء بمنشأ وزاري.

الاختبارات المستقبلية: clean+upgrade migration مع صفوف FINAL/DRAFT قديمة وFollowUps قائمة؛ عدم تحويلها أو تغيير إسقاطها؛ نموذج جديد وإنشاء/حفظ/تزامن/إتمام/لقطات/عدم تعديل النهائي؛ معايير ذات مفاتيح ثابتة وتحقق نصوص عربية بلا أرقام مستنتجة؛ scope وCSRF وأخطاء آمنة؛ إخفاق AuditLog يُرجع الإتمام؛ FollowUp من تقرير جديد ثم regression TASK-053/G5؛ E2E محرر RTL ولوحة المفاتيح؛ coverage لكل خانة مصدر وتطابق ترتيب وطباعة A4 مرئية لاحقًا ببيانات اصطناعية. عقد التنفيذ المحدد في [TASK-054](TASK_054_INSPECTOR_VISIT_REPORT_V1.md)، والطباعة خارجها. ADR-013/TASK-060 مستقلان.
