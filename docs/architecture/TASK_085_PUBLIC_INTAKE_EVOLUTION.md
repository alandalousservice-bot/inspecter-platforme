## Purpose and trust boundary

The existing public route is `POST /api/v1/public/districts/:districtId/submissions`. A Teacher has no account. Each POST creates an independent, unverified `TeacherSubmission` for the district in the path. The Inspector reviews it; only an explicit `ACCEPT` creates a new Teacher inside the existing decision transaction. A declaration does not approve an Institution, a qualification, a supplementary workplace or a schedule. Accepted scalar seeds initialize a **new** Teacher as the Product Owner specifically allowed; they do not verify identity or create relationships, update an existing Teacher, or propagate subsequent submission edits. Inspector profile corrections remain authoritative.

The current required identity/contact/professional fields and required `workplace` object remain required and unchanged. Existing optional `confirmationDate`, legacy free-text `qualifications`, and `notes` remain supported with their present acceptance behavior: `confirmationDate → Teacher.confirmedAt`, free-text `qualifications → Teacher.qualifications`, and `notes` stays submission-only. `SUBSTITUTE` remains the distinct fifth required `professionalStatus` choice, implemented in TASK-080. No new field below is required.

## Field decisions

`Public` means inclusion in a **new** public request. All new text is optional, non-null and nonblank **when supplied**; omission means unknown. Dates are optional exact `YYYY-MM-DD` calendar dates. The limits are Unicode code points after normalization; qualification and workplace object limits are specified below. `Seed` means copy the normalized, persisted declaration to a newly created Teacher on ACCEPT only. `History` means retain on the submission without an automatic master-data write.

## Public JSON and validation

The same v1 endpoint evolves additively. Existing required keys stay: `firstName,lastName,dateOfBirth,placeOfBirth,phone,email,professionalStatus,employmentDate,workplace`. Existing optional keys stay: `confirmationDate,qualifications,notes`. The required `workplace` still requires `institutionName,municipality,institutionAddress,directorPhone` and may additionally contain optional `institutionEmail`. New optional top-level scalars are the ten seeded fields plus `firstEducationAppointmentDecisionNumber`, `institutionAppointmentDate`, and `institutionAppointmentNumber`; the seed count excludes the existing confirmation date. New optional arrays are `structuredQualifications` and `supplementaryWorkplaces`. No `districtId`, `institutionId`, Teacher ID, assignment ID, period, administrative note, mark or status lookup key is accepted from the body. Top-level and every nested object are strict; unknown keys and explicit `null` for any new field/array/object are rejected. Omitted arrays and `[]` both mean no declarations; the form omits empty arrays. A malformed element is rejected as a whole request, not silently dropped.

Text uses Unicode NFC, trim, collapsed display whitespace, control-character rejection, code-point limits above and no truncation; optional `""`/whitespace-only input is invalid if sent. Preserve the established phone normalization (Algerian fixed/mobile) and email normalization (trim, domain lowercased, local part unchanged). The accepted free-text `qualifications` and `notes` retain their existing distinct behavior; do not parse or rewrite historical values. Calendar dates must be real exact `YYYY-MM-DD` values, stored as PostgreSQL DATE without UTC/time-zone conversion. Preserve the existing birth/employment/confirmation validation. New administrative/qualification dates have no new cross-field HR-law order, status inference or blanket future-date rejection. Date and number fields are independent; classification labels and effective date may be partial.

`structuredQualifications?: Array<{name:string,issuingBody?:string,qualificationDate?:string}>`: 0..5 rows, `name` 1..200 required; `issuingBody` 1..200 optional; `qualificationDate` optional real DATE. No uploaded certificate, qualification-type enum, document ID or legacy-text parsing. Preserve the submitted order and distinct rows even when text repeats; no automatic deduplication. `supplementaryWorkplaces?: Array<{institutionName:string,municipality?:string,institutionAddress?:string,directorPhone?:string}>`: 0..3 rows; `institutionName` 1..200 required, `municipality` 1..150 optional, `institutionAddress` 1..300 optional, and `directorPhone` optional with the existing <=20-code-point raw/Algerian phone validation and canonical stored form. Preserve order and repeated names without asserting identity. No validity dates, hours, role, Institution ID or automatic main/secondary classification. The declared home email is optional under `workplace`, not a Teacher contact email.

The existing 32 KiB JSON body cap and rate limit of **10 attempts per trusted IP per 15 minutes** remain. Array and string limits are additional; a combined payload over 32 KiB is rejected even if each field is individually within its limit. The client may warn before sending based on encoded byte size, but the API remains authoritative. No OTP, teacher account, autosave, challenge or `Idempotency-Key`; every successful POST creates its own submission. Invalid values return the existing safe error envelope with field paths only, never echoed values. The route still validates the path district and active membership availability without revealing people, duplicates or district records.

Success remains `202 {data:{receiptId:<uuid>}}`, `Cache-Control: no-store` and request ID, with no submitted PII, status, duplicate hint or public lookup. A retry is a new submission. `GET /submissions` list projection, duplicate candidate reasons, and decision endpoint body/response do not change. ADR-011 still compares only accepted phone/email/name-and-birth-date signals among eligible submissions; administrative values, workplace text and qualifications are never new matching keys.

## Persistence and migration plan

One **additive forward-only TASK-085 migration** is required; no previous migration is edited. Keep existing `TeacherSubmission.submittedProfile` JSON byte-for-byte for historical rows and preserve its present G3/TASK-041 payload conventions. New fields are persisted in **typed nullable submission columns**, not an arbitrary new JSON blob. The public POST stores the existing payload keys in `submittedProfile` and writes new declarations in columns/children in the same transaction. The Inspector detail projection composes them on read; the acceptance service reads the persisted typed seeds after the submission is claimed. Do not use the public request body as the decision-time source of master values.

Add these nullable `TeacherSubmission` columns, matching current Teacher types/bounds where applicable: `birthProvince varchar(100)`, `professionalFramework varchar(120)`, `firstEducationAppointmentDate DATE`, `firstEducationAppointmentDecisionNumber varchar(120)`, `firstInstallationDate DATE`, `traineeshipDate DATE`, `institutionAppointmentDate DATE`, `institutionAppointmentNumber varchar(120)`, `administrativeCategory varchar(100)`, `administrativeSection varchar(100)`, `administrativeGrade varchar(100)`, `administrativeClassificationEffectiveDate DATE`, `personalAddress varchar(300)`, and `declaredHomeInstitutionEmail varchar(254)`. All remain NULL for legacy/omitted data; no guessed backfill, default value or duplicate Teacher column. Add bounded/nonblank DB checks consistent with the existing TASK-080 approach where feasible; Zod owns NFC and semantic validation. No new index for fields that are not searched.

Add `TeacherSubmissionQualificationDeclaration(id UUID PK,submissionId UUID FK,position SMALLINT,name varchar(200),issuingBody varchar(200) NULL,qualificationDate DATE NULL,createdAt timestamp default now())`. Add `TeacherSubmissionSupplementaryWorkplaceDeclaration(id UUID PK,submissionId UUID FK,position SMALLINT,institutionName varchar(200),municipality varchar(150) NULL,institutionAddress varchar(300) NULL,directorPhone varchar(20) NULL,createdAt timestamp default now())`. Child FKs reference `TeacherSubmission.id` with `ON DELETE RESTRICT, ON UPDATE CASCADE`; these are immutable historical declarations with **no update/delete API**. Each has `UNIQUE(submissionId,position)` (also its parent-leading retrieval index) and a CHECK `0 <= position < 5` or `< 3` respectively, enforcing the array caps at DB level. The public POST assigns zero-based positions; GET orders by position. No content uniqueness, Institution/TeacherQualification/TeacherSupplementaryWorkplace FK, audit event, search index or backfill. Existing submission rows get zero children. Prisma relation additions are planned only for the later implementation; this gate changes no schema.

Legacy submissions must remain readable: new scalar detail facts return explicit `null` and collections `[]`; old `submittedProfile` JSON is not rewritten or parsed into new columns/children. The pre-TASK-085 public request shape remains valid because all additions are optional. The old G3 workplace shape stays readable but is **not** re-enabled for new POSTs. Acceptance of a legacy submission must retain its previously applicable mapping and must not fabricate new values. Any future correction/retention policy is outside TASK-085 and ADR-014 remains OPEN.

## Inspector review and ACCEPT

`GET /api/v1/submissions/:id` keeps the existing `submittedProfile`, `declaredWorkplace`, `potentialDuplicates` and `acceptedTeacherId`. Add `declaredAdministrative` with **all 13** new top-level scalar facts as explicit `string|null`, including dates formatted `YYYY-MM-DD`; `declaredWorkplace` gains `institutionEmail:string|null`; add `structuredQualifications` and `supplementaryWorkplaces` arrays in saved order. Do not put the new facts in the list projection or potential-duplicate summaries. An older submission shows `null`/`[]` and «غير مصرح به», never a fabricated value. The detail route checks current Inspector district membership before returning any new private fact. No public detail/status route is added.

`POST /api/v1/submissions/:id/decision` keeps its strict `{action,expectedStatus}` request, status transitions and response. On `ACCEPT`, under the existing transaction/conditional claim, create exactly one Teacher with the current seed mapping **plus** `birthProvince,professionalFramework,firstEducationAppointmentDate,firstInstallationDate,traineeshipDate,administrativeCategory,administrativeSection,administrativeGrade,administrativeClassificationEffectiveDate,personalAddress` from persisted nullable columns. Keep `Teacher.institutionId=NULL` and the three home-specific appointment facts NULL. Do not copy the two decision/appointment numbers or institution appointment date, home email or structured/extra-workplace declarations. No `Institution`, `TeacherQualification`, `TeacherSupplementaryWorkplace` or `WeeklySchedule` row is created. `REJECT/INTERNAL_REVIEW` keep all declarations on the submission but create no Teacher. Retries and concurrent decisions keep the existing one-winner `409` behavior; no auto-merge/update into an existing Teacher.

Audit remains the existing atomic `TEACHER_SUBMISSION_ACCEPTED/REJECTED/INTERNAL_REVIEW` event: only IDs and the already approved structural metadata, no declaration values, address, reference number, qualification or workplace prose. Public creation still writes no AuditLog. No raw body, new private field value or credential in application logs, errors or traces. Teacher directory, Visit/FollowUp/report list, unrelated report snapshots and public receipt remain unchanged. A newly seeded private address is visible only on existing authorized Teacher profile/card surfaces.

The public form uses Arabic RTL grouped sections and keeps the current required flow concise; new sections may be optional disclosure groups rather than a second mandatory step. Name sections «بيانات مصرح بها», «المؤسسة المصرح بها», «مؤسسات تكملة النصاب المصرح بها», «المؤهلات والشهادات المصرح بها» where trust status matters. It remains usable on a phone, with accessible labels, focus, error and loading states and bounded add/remove controls for the two arrays. Submission detail groups personal/professional, appointment/installation, classification, declared home/extra workplaces and structured qualifications, and visibly distinguishes declaration from the authorized Teacher record. Inspector uses existing TASK-081/082 workflows to enter approved child records after review; those workflows do not consume declaration rows automatically.
